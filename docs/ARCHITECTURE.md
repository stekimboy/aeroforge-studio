# Architecture, invariants and doctrine

The compact statement of how AeroForge is built and what must not change. Read this before editing anything under `aeroforge/`.

## What AeroForge Is

A local web app (`aeroforge/`) that designs **RC aircraft**. Give it an aircraft type, a mission, a cruise speed and a hard size box; it solves the coupled weight/aero/stability problem, renders the result in 3D and exports CAD. Every number shown comes from a real calculation — no placeholder physics.

**v2 pivot (2026-08-12, reversing the earlier flying-wing-only decision):** the app is growing back multi-type support. `airplane_type` selects the aircraft family — `flying_wing` (the mature v1 path, saved as tag `v1` on github.com/stekimboy/aeroforge, whose behavior and layout must NOT change) and `conventional` (wing + fuselage + horizontal/vertical stabilizer), with an "any" mode that optimizes across types from bare parameters. The v1 flying-wing invariants below are **scoped to the flying-wing path**; conventional gets its own analogous invariants as it lands. The hardware doctrine (measured servo pockets, round Ø8.25 wire pipes, print-in-place hinges, per-face clearances, existence-checked cuts) applies to EVERY type.

**v3 (2026-08-16):** eight types — plus four **configuration axes** exposed as their own choices: tractor vs pusher, motor count, tail type (`conventional` / `t_tail` / `v_tail`), and wing position (`high` / `mid` / `low`). They ride a `design["config"]` block whose absent keys mean "the type's researched default", so a bare v2 request still produces byte-identical output. The hardware doctrine is unchanged and applies to every type. **v3.1 (2026-08-21): `biplane` and `glider` are REMOVED outright** — six types remain: `flying_wing`, `conventional`, `delta`, `canard`, `tandem`, `twin_boom`. Their physics modules and test suites were deleted; the biplane CAD builder sits dormant in `cad/multiwing.py` (shared machinery), unreachable through the table-driven dispatch. **Known gap, flagged not fixed:** `config_axes.apply_tail_type` / `apply_wing_position` / `apply_motor_layout` now have NO physics consumers — only the deleted glider ever wired them, so the tail-type / wing-position / motor-layout selects the registry still advertises for `conventional` and `twin_boom` are accepted and silently ignored. Wiring them (or narrowing the registry) is an open decision.

**Code map:** `aeroforge/CODE_MAP.md` - module-by-module "edit here for X" tables, function handles and the test/tool that proves each claim; the open items and the run recipe are in the README ("Quick start", "Known gaps"). **Rear-hollow rule:** the rear hollow must be proven in cross-sections of the actual output geometry (`tools_audit_rear_hollow.py`, `tools_probe_cavity.py`), never in builder flags; every change there is checked against a real generation.

**`aeroforge/SPEC_FLYING_WING.md` is the binding contract** for the flying-wing domain model, design-dict schema, CAD topology and invariants. `aeroforge/docs/V2_PLAN.md` and `aeroforge/docs/V3_PLAN.md` are the working contracts for the multi-type architecture, and `aeroforge/RESEARCH_TYPES_V3.md` is the cited-band dossier behind every v3 number. 

## Commands

Run everything from `aeroforge/` using the venv interpreter directly — `.venv/Scripts/python.exe` on Windows, `.venv/bin/python` on macOS/Linux — rather than activating.

```
run.bat                                        # full launch: venv + deps + server + browser
.venv/Scripts/python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
.venv/Scripts/python.exe -m pytest tests/ -q   # full suite (~45 min; CAD dominates - run per-planform with -k while iterating)
.venv/Scripts/python.exe -m pytest tests/test_optimizer.py -q
.venv/Scripts/python.exe -m pytest tests/test_cad_export.py -k bell -q
.venv/Scripts/python.exe -m pytest tests/test_conventional_physics.py -q   # tailed physics (~100 s)
.venv/Scripts/python.exe -m pytest tests/test_conventional.py -q           # tailed CAD (~30 min, full builds)
.venv/Scripts/python.exe -m pytest tests/test_type_dispatch.py -q          # v3 type->CAD-module dispatch (~5 s, never builds)
.venv/Scripts/python.exe -m pytest tests/test_multiwing_physics.py tests/test_boomglider_physics.py -q   # v3 physics (~60 s)
.venv/Scripts/python.exe -m pytest tests/test_multiwing.py -q              # canard/tandem CAD (full builds)
.venv/Scripts/python.exe -m pytest tests/test_twinboom.py tests/test_delta_cad.py -q   # the other v3 CAD
.venv/Scripts/python.exe tools_make_validation.py   # regenerate VALIDATION.md from real runs
```

Python 3.12 is used (3.11 isn't installed here); `run.bat` prefers 3.11 then falls back. Windows PowerShell 5.1 has no `&&` — use `;` or the Bash tool.

## Domain model

Four **planform families** (`physics/config_defs.PLANFORMS`), each with its own sweep / taper / AR / washout bands:

| key | what it is | reference airframes |
|---|---|---|
| `swept` | swept sport / FPV wing | Skywalker X5, SonicModell AR Wing |
| `bwb` | blended wing body, deep payload bay | Ritewing Drak |
| `plank` | unswept, near-constant chord, strong reflex | PW-51, Zagi-plank |
| `bell` | bell-shaped spanload, big washout, **no fins** | NASA Prandtl-D, Horten |

Four **missions** (`MISSIONS`): `sport`, `fpv_cruiser`, `thermal_floater`, `park_flyer`.
Four **vertical-surface arrangements**: `winglets`, `twin_fin` (inboard, X5 style), `center_fin`, `none` (bell only).

The **conventional** type has its own analogous registry: five **styles** (`config_defs.CONV_STYLES`): `trainer`, `sport`, `aerobatic`, `floater`, `speed` — each a row of the coefficient table in `RESEARCH_CONVENTIONAL.md` (V_H/V_V targets, tailed SM, AR/taper/dihedral, wing position, tail arm, non-reflexed airfoil). `AIRPLANE_TYPES` is the registry the API validates against; `"any"` is a request mode resolved by `variants.py` into concrete typed designs.

**v3 — eight types, and the axes each one legally offers.** Every entry of `AIRPLANE_TYPES` carries an `axes` dict (`motor_layout`, `n_motors` as a `[min, max]` pair, `tail_type`, `wing_position`); an **empty list means the axis does not apply** to that type and the frontend hides its row, while a one-entry list means the value is fixed by that type's practice and is shown but not chosen. The bands behind them are cited per section to `RESEARCH_TYPES_V3.md`:

| type | motor layout | motors | tail | wing position |
|---|---|---|---|---|
| `flying_wing` | pusher (fixed) | 1 | — | — |
| `conventional` | tractor / pusher | 1–2 | conventional / t_tail / v_tail | high / mid / low |
| `delta` | **pusher** / tractor | 1 | — (planform fins) | — |
| `canard` | pusher (fixed) | 1 | — (tip fins) | **mid** / high / low (rear wing) |
| `tandem` | tractor / pusher | 1 | — (aft fin) | high (fixed by the gap rule) |
| `twin_boom` | **pusher** / tractor | 1–2 | conventional (H) / v_tail | high (fixed) |

Bold marks a default that differs from the list's usual first-is-tractor reading. (`biplane` and `glider` rows removed with the types, 2026-08-21; `n_motors: 0` — the glider's pure-sailplane privilege — is now rejected by the schema.)

## Architecture

Request flow: sidebar (`frontend/app.js`) → `POST /api/generate` → `physics/variants.py` runs `optimize_design` **five times** with different planforms and targets → five design dicts returned immediately → `GET /api/preview/{id}.stl` builds each wing's CAD lazily on demand.

- `backend/physics/` — `atmosphere` (ISA, Sutherland, Reynolds), `airfoils` (analytic NACA + **reflexed** sections; polars from NeuralFoil with a thin-airfoil fallback), `aero` (lift, drag build-up, stall), `stability` (MAC, spanwise strip model for NP/trim/washout, `flying_wing_fin` sizing, bell spanload), `weights`, `optimizer` (constrained sweep over span/AR/sweep/taper + Nelder-Mead polish), `variants` (the five characters), `guidance` (per-design builder advice + Learn articles), `config_defs` (planforms, missions).
- `backend/cad/geometry.py` — the airframe is **one continuous full-span loft**, tip to tip. There is no separate fuselage solid: the centre body IS the wing, its sections simply get deeper and longer toward the root. `build_design_parts` returns named parts (`airframe`, fins/winglets, canopy, cg_marker) for the STEP assembly; `build_design_solid` fuses the same parts into one healed solid for STL/preview. Keep both signatures stable.
- The centre body is **hollowed** into an equipment bay, and the cap above it is extracted as a separate `hatch_lid` part (shelled against a copy of itself dropped by one wall thickness, so it inherits the crown's curvature at skin thickness). `build_design_parts` separates the lid; `build_design_solid` keeps it attached and only **scribes** its outline, because the one-piece STL has to stay a single watertight solid. A structural motor-mount boss is fused into the airframe and its screw holes drilled through boss + skin + bulkhead together.
- **Every cut is tessellation-checked** (`_tessellates_cleanly`). Cutting the bay or scribing the lid produced solids that `isValid()` called fine and OCC then refused to mesh — the exported STL simply lacked 73 mm of nose. A cut is kept only if the result still meshes completely; the bay falls back through a ladder of narrower cavities.
- `backend/cad/hinges.py` / `hatch.py` / `servos.py` / `conduits.py` — the hardware, each owning its own clearances and sources. `hinges` cuts the elevons free and hangs them on print-in-place captive pins (RC double bevel + cove, 2 per surface). `hatch` builds the equipment bay and its canopy. `servos` cuts the 9 g (SG90) servo pockets, fuses a control horn into each elevon and solves the linkage. `conduits` routes the motor and servo wire runs as self-supporting gabled channels. `geometry` orchestrates them; none imports a sibling.
- `backend/cad/exporters.py` — `export_step` writes a CadQuery **assembly**; `export_stl`/`write_stl_verified` write one watertight solid; `export_stl_parts` writes a zip of one STL per named part plus a manifest. **A full STEP is ~28 MB and takes ~160 s to build**, so `/api/export` caches one file per (design, format) under the exploded-preview lock — never make export rebuild per click.
- **v2 multi-type plumbing** — `airplane_type` dispatches at exactly four seams, nowhere else: `physics/optimizer.optimize_design`, `physics/variants.generate_variants`, and the two public entry points of `cad/geometry.py` (`build_design_parts`/`build_design_solid`). Conventional lives BESIDE the flying-wing code: `physics/stability_conv.py` (tail-volume NP per Nelson eq. 2.34, Munk fuselage term, decalage trim), `physics/conventional.py` (evaluate/optimize/variants + any-mode), `cad/conventional.py` (superellipse fuselage loft + dihedral wing + stab/fin; ailerons via the elevon hinge machinery, elevator split into left/right panels around the tail post, rudder hinged and horned in a +90° rotated build frame; elevator/rudder servos in the fuselage bay; every pipe/pocket/horn rule reused verbatim). Conventional part names: `airframe`, `aileron_l/r`, `elevator_l/r`, `rudder`, `hatch_lid`, `cg_marker`.
- **v3 multi-type plumbing** — the same four seams, now resolved by **tables rather than if-chains** so the registry and the dispatch cannot drift apart (`tests/test_type_dispatch.py` asserts exactly that). Physics: `variants._TYPE_VARIANTS` maps each type to a `generate_*_variants` entry point in its own module — `physics/delta.py`, `canard.py`, `tandem.py`, `twinboom.py`, each with `conventional.py`'s signatures; the flying-wing path imports none of them (`biplane.py` and `glider.py` were deleted with their types, 2026-08-21). CAD: `geometry._TYPE_MODULES` sends `conventional` → `cad/conventional.py`, `canard`+`tandem` → `cad/multiwing.py`, `twin_boom` → `cad/twinboom.py`, and `flying_wing`+`delta` through the untouched tailless path in `geometry.py` itself. `physics/config_axes.py` owns the four axes (`apply_tail_type` V-tail/T-tail sizing, `apply_wing_position` dihedral/stability deltas, `apply_motor_layout` mass/CG/mount stations, `engine_out_check`) and `stability.py`/`stability_conv.py` stay frozen — but note the v3.1 gap above: with the glider gone these transforms currently have **no consumers**. A type added to `AIRPLANE_TYPES` without a dispatch entry would **silently build as a flying wing** — that is precisely how `multiwing.py` sat finished-but-unwired while every per-type CAD suite passed, because those suites import their builder module directly.
- **CAD runs in worker processes** (`backend/cadjobs.py`, 2-worker spawn pool, `AEROFORGE_CAD_WORKERS` overrides, `0` = inline): OCC holds the GIL, so in-process builds serialized. Job functions call the same builders with the same tolerances — artifacts are byte-identical (proven, `docs/PERF_NOTES.md`); caching/locks stay in `api.py`; `paths.py` keeps cadquery imports out of the server process. Never re-introduce a CAD import into `api.py`/`main.py`.
- `frontend/` — dark-navy UI in three columns: docked design-data panel on the LEFT (`#datapanel`, tabbed Specifications / Design notes, collapsible to a rail), 3D stage + variant gallery in the middle (`#workspace`), input sidebar on the right (`#sidebar`). Nothing but the legend and transient status pills floats over the viewport. Variant gallery uses shared-context mini 3D previews; the viewer draws CG/NP/MAC/motor/box overlays.

## Invariants (enforced by tests — don't regress them)

- Every design fuses into **exactly one** valid solid; nothing protrudes ahead of the nose datum `x = 0` (all CG/station numbers are measured from it).
- The airframe is a single full-span part. A separate `fuselage`/`pod` solid, or split `wing_left`/`wing_right` parts, means the blended-body topology has regressed — that pod-plus-panels build is exactly what made the old output read as parts stitched together.
- CAD bbox stays within the recorded `geometry` totals (span / `length_total_m` / `height_total_m`) + 2 mm, and those totals fit the author's box. If a part needs more room, widen the budget in the optimizer — never silently clamp it.
- Exported STL mesh area ≥ 98.5% of BRep area. OCC silently skips pathological boolean-trimmed faces, which produced a real "hole in the skin" bug; lofts are segmented with shared boundary wires and `_heal` (ShapeFix) runs after fuse and after cuts.
- Physics: CG ahead of NP, static margin **0.03–0.15** (tailless band, not the tailed 0.04–0.20), `V_cruise ≥ stall_factor × V_stall`, L = W at cruise, L/D 5–24, fits the box.
- **Handling is checked on all three axes, not just pitch** (`physics/handling.py`): `Cn_beta > 0` (weathercock), `Cl_beta < 0` (dihedral effect), and trim must not eat more than 75% of the elevon travel. Thresholds are tailless-calibrated — a wing runs an order of magnitude below a tailed model's `Cn_beta` and is flown that way, so tailed numbers would flag every design. Proverse yaw is a **roll-input** property (the bell spanload's induced angle reverses at η=0.577), not a sideslip one; a bell wing is genuinely soft in `Cn_beta`.
- Every design uses a **reflexed** (positive `Cm0`) section — a tailless wing has no tail to trim against.
- **Real RC proportions.** Root chord ≥ 0.30 × span for `swept`/`bwb`, and the centre body must be deep enough to hold the pack. Real wings are short and deep: X5 Pro is 1280 mm span / 717 mm root (0.56), AR Wing is 900/482 (0.54). AR 5–6 with a 0.20 × span root is a glider planform and is what forced the old pod-on-top look.
- Vertical surfaces are 2–9% of wing area, sized from real flying-wing practice rather than the tail-aft `V_V` band; reported `V_V` is legitimately far below 0.02–0.05 because the fin sits ~one root chord behind the CG. Do not "fix" it by scaling the fin — see `stability.flying_wing_fin` and DECISIONS.md. Bell-spanload designs carry **zero** vertical area.
- Five variants always returned, spanning ≥ 3 planform families.
- **The servo arm and the control horn share a plane, by construction.** `servo_bay(arm_y_mm=…)` places the servo CASE so the ARM lands on a given plane; `control_horn(align_world_y=…)` solves its own station on the hinge line to match. Residual must be ≈0 — a pushrod is straight wire, and an offset becomes side load on the servo bushing, unequal throws and a reamed horn hole. Never place the horn at a fixed `station_frac` and let the arm fall where the case puts it (that was worth 64.6 mm). Radii are matched (`arm_r_mm` = `r_design_mm` = 11.0) so the four-bar is a parallelogram at ratio 1.000.
- **Every mating pair that moves gets clearance, and each figure carries its source.** Elevon↔wing 0.50 mm at the hinge gap but **1.00 mm at each spanwise end face** (`end_clearance_mm` — decision: side gaps doubled, hinge/TE untouched), hinge pin 0.35 mm radial, servo pocket **0.25 mm per face, the exact inverse of the builder's own measured servo model** (`REAL SG90.stl` at the repo root — **the author's own CAD model of the servo**, not a download; decision 2026-08-19 replacing the HXT900 of thing:1251554, whose reference folder has since been deleted from the repo; the first `SG90-NEW-SERVO/SG90.stl` they supplied was "the wrong file" and is superseded. Same 9 g class, far easier to buy, and the doctrine below is unchanged; the full-width gear head above the case top is real and the FS90 drawing's output-boss-only picture is not; each measured feature is its own vertical-prism region: case, lead stub, ears, head, spline/hub. The measured part is TALLER than the datasheet family — 32.55 to the spline top, 24.75 case — and the part wins over the catalogue. This model draws no wire tab, no grommet and no ear bores; the lead numbers keep their earlier evidence and the M2 pilots land mid-ear) — see `hinges.HINGE_DEFAULTS`, `servos.SERVO_CLEARANCE_MM`. Every wire run — servo and motor, including the belly entry hole — is **one STRAIGHT pipe of OVAL cross-section, 12.0 mm wide × 8.25 mm tall (decision), the bay is locally enlarged when that is what the perpendicular run needs (on the flying wing and delta the bay CAVITY ITSELF continues aft — a ROOT PRINCIPLE inside `hatch.build_bay`, decision 2026-08-26: the extension is surveyed/planned/banded by the bay's own machinery, hull-following inner surfaces, ≥3 mm rear walls, hinge/TE-guarded taper, hatch and lid unchanged, per-station band published as `bay_mm["cavity_stations_mm"]` and the servo tubes aim at it at their own station; a fitted channel "small tube" and every add-on cutter variant were explicitly rejected; the box side-gallery survives only as last-resort fallback — and `tests/test_cad_export.py` FAILS on it; a centre fin caps only the HATCH, the cavity continues under it at full section and the fin's root is trimmed to the cavity roof at fuse time so it follows the inner hull (`geometry._FIN_ROOT_BURY_MM`; the straight 0.35 t root would stand in the compartment as a centre wall), and `tools_probe_cavity.py` sweeps 18 configurations to prove the extension carves on every one (decision); side trench / full-width floor chamber on the conventional, aft gallery through the fuselage or pod on canard/tandem/twin-boom — the forward-bay types where a side entry is geometrically impossible and the run angles like the motor's — `bay_expansion` in the run's report names which; each is a generous chamber that merges into the bay hollow, not a narrow right-angle shaft — decision 2026-08-24, round 7), and a line that cannot stay inside the skin refuses honestly (`conduits.straight_conduit`) rather than bending or tilting) — of **CONSTANT cross-section end to end** (decision)** where it opens into the servo pocket, the belly skin, and the bay, and the servo pipe's pocket mouth opens **AT the measured lead grommet** (shaft-side end face, where the wire actually leaves the case — decision; the mouth-within-2.5 mm-of-grommet property is test-enforced, the old position made the wire fold back under the case) (decision). The horn carries **one plain 2.5 mm hole**, rim ≥2.75 mm all round (decision). The hatch magnet pockets are bored at **exactly Ø8.15 — `MAGNET_FIT_MM` is zero and stays zero**, the builder's number already contains its own allowance (decision); pad/lug widths scale with the bore, and a canopy lug is fused only after it provably shares volume with the lid, with a recut against the lid itself when the station-loft band misses the true skin (`hatch._fit_magnets` — the bwb shipped "airframe pads only" for as long as nobody checked). With the cavity extended, the AFT pad is a short shelf hanging from a riser into the roof just behind the aperture (`hatch._AFT_RISER_LEN_MM`) — never a rib to the extension's end wall (decision). The motor leads enter through the **12.0 × 8.25 mm oval belly hole near the mount**, which is now simply the skin breach of ONE straight pipe running direct to the bay (`geometry._motor_entry_run`) — the motor tube may angle downwards, it may never bend.
- **A wing must be able to bury its own aileron servo, and the optimizer — not the CAD — is what makes room.** The servo lies on its side, so the pocket is a world-vertical box 12.4 mm deep running 33.0 mm along the chord. What the section owes it is **min(crown) − max(keel) across that whole footprint, not peak thickness** (~0.89 of max t on a NACA 2412, less on a cambered 4412), minus what dihedral and twist cost at the corners (`SERVO_SPAN_MM·tan Γ + window·tan θ` ≈ 1.7 mm on an ordinary 2°/2° wing). `twinboom.servo_chord_floor_m` bisects that to a minimum local chord and `evaluate_twinboom` lifts the chord until the aileron-root station clears it — chord alone does not predict the fit, so never "fix" this by nudging AR bands. A design that still misses (AR already on its researched hard floor) records `geometry.servo_chord_floor.fits = false` rather than only warning from the CAD. Physics restates four of `servos.py`'s numbers because it must not import `backend.cad`; `test_twinboom_servo_pocket_constants_match_the_cad` keeps the copy honest.
- **Fuses whose absence matters get one too — a feature is believed only when it can be CLASSIFIED in the result** (`cad/geometry.fuse_feature`, shared by conventional/multiwing/twinboom). `base.fuse(fin)` can return a shape that is `isValid()` and exactly one solid and does not contain the fin: that is how the biplane shipped with no vertical surface at all, and the failure only surfaced three steps later as a rudder that had split a chip off the tail cone. The check is **geometric, never volumetric** — `Volume()` on these spline solids is computed to a loose default tolerance and disagrees with itself by tens of thousands of mm³ on shapes that classify perfectly. When the boolean misbehaves the ladder retries with the operands' tessellation dropped, then rebuilt through BRep (measured: the freshly lofted *addition* carries the bad state, not the base), then fuzzy-valued; a feature that still will not fuse is named in the warnings instead of vanishing.
- **Cuts whose absence matters get their own existence check.** `isValid()` says a shape is well-formed, not that an operation did what was asked: horn keyholes once vanished server-side while every step reported success. The keyholes are bored into the FUSED elevon (last, so nothing downstream can lose them) and each bore is verified by point classification, with a separate-cylinder retry and a builder-facing warning on failure (`info["holes_cut"]`). Same doctrine as the mesh gate.
- **Wire runs end INSIDE the bay void.** The hatch ladder shrinks the cavity about its centre, so aim at `bay_mm["x0_mm"]/["x1_mm"]` (the carved void), never at nominal `bay_start + bay_length` — a channel driven past the nominal wall can still dead-end inside the real bulkhead.
- The servo pocket houses the **servo plus hub swing room** — no arm well. The boss patch clears the fitted horn's 8.5 mm hub with **8 mm of chordwise swing room per side** (`servos.HORN_SWING_ROOM_MM` — decision 2026-08-20, widening the 15 mm slot to 25 mm because the printed part "restricts the servo movement too much"; the extra aft reach is counted against the hinge margin in `servo_bay`'s aft cap); the blade works below the skin in free air (`arm_free_deg` reports the swing, warns if under what the linkage needs).
- **The horn is a rounded, beveled triangle, AT MOST 15 mm below the skin (`protrude_max_mm`, a hard cap), set as far aft as that height can drive, and it stands STRAIGHT relative to the wing** — extruded and bored along world y, square to the servo arm's swing plane, never along the hinge sweep (decision); lever geometry stays computed perpendicular to the true hinge axis, converted by 1/cos(sweep). The tip is a circular lobe centred exactly on the single 2.5 mm bore so the rim is 2.75 mm all round by construction; the blade root fills the section to just under the upper skin (the root band is *measured* by classification — a reflexed TE curls above the hinge-axis plane, and the classifier itself is corroborated because it throws phantom hits along the razor lip). For the near-chordwise pushrod, the moment arm is the hole's depth below the hinge axis; aft offset adds rake, and rake is where the four-bar dies — measured: 50° cap (`rake_max_deg`) is the sweet spot, 55° halves the up-throw, 60° toggles to zero. So the height cap fixes the hole line at ~depth×tan50° ≈ 18 mm aft (radius ~23 mm, throws −25/+22° for ±45° servo); the earlier full-trailing-edge anchor (round 3) was superseded by the author's own 15 mm cap — the two are physically incompatible, don't restore either at the other's expense. `linkage` searches the arm-neutral clock and ships the result in `meta["servos"]["linkage"]`.
- "If it looks right, it flies right": geometry must match real RC practice, not just satisfy the equations. Anything that would make a builder squint is a bug even when the numbers close.

## Deliberate departures from the original build brief

Recorded with reasoning in `aeroforge/DECISIONS.md` — read it before "fixing" something that looks wrong:

- ~~**Flying wings only.**~~ Superseded twice by the author's own reversals: v2 (2026-08-12) brought back `conventional`, v3 (2026-08-16) brought the count to eight. Kept here because the v1 code still reads as if the wing were the only type, and it deliberately does — the tailless path was frozen, not generalized.
- **No propulsion sizing.** Thrust, power, prop, Kv, cells and battery specs are gone; the app designs airframes. Motors survive only as count + positions (red markers in the viewer). A lumped power-system **mass** allowance (~28% of AUW) stays because weight drives stall speed and CG.
- **Objective is specific drag** `100/(L/D)`, not power. Size-normalized so it doesn't collapse to micro aircraft; paired with a Reynolds floor penalty and proportion terms.
- Optimizer is a structured sweep + Nelder-Mead polish (scipy), not end-to-end CasADi.
- Watertightness is verified as closed BRep + ≥98% manifold edge pairing (OCC leaves T-junctions on every boolean).

## Conventions

- Physics equations carry a comment citing the relation they implement; keep that up.
- Use `pathlib.Path` everywhere; no Unix-only shell commands.
- Prefer editing the CAD section-shape functions over post-hoc clamping — geometry should follow the physics, not fight it.
